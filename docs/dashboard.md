# Experimental local report viewer

The Svelte viewer under web/ displays a report v1 JSON file that a user explicitly chooses or drops into the page. It decodes file bytes with strict UTF-8 handling and rejects malformed byte sequences instead of silently replacing them with U+FFFD; this keeps browser intake aligned with the Python UTF-8 file readers. Before parsing, the browser rejects duplicate object keys (including equivalent escaped spellings) for both report-v1 and repeat-analysis-v1 files. After parsing, it rejects any numeric value that JavaScript represents as non-finite (for example, `1e400`) rather than later displaying `null`; this includes exponent-overflow values rejected by Python's strict loader. Before parsing, it also rejects integer-form JSON tokens outside JavaScript's safe integer range (for example, `9007199254740993`) to avoid silent integer rounding. It checks the original decimal digits directly, so this guard does not construct an unbounded-precision integer from attacker-controlled input. Decimal and exponent-form numbers are still represented using JavaScript numbers; this is not an arbitrary-precision numeric parser. Imports exceeding 256 levels of nested JSON arrays/objects are rejected before parsing, and braces/brackets inside JSON strings do not count toward this limit. The depth scan only closes a level when the closing delimiter matches its opener; stray or mismatched closers in malformed input cannot reduce the measured depth before native JSON parsing rejects the file. This nesting guard runs first. A second preflight guard rejects inputs exceeding 500,000 JSON tokens (counting string/member-name tokens, scalar values, and array/object delimiters) before parsing. Both limits run before duplicate-key scanning, so deeply nested or token-heavy input is rejected before per-object key sets are allocated. It provides run summaries, context differences, finding search and filters, a chronological timeline of evidence referenced by findings, source-evidence details, and declared uncertainty. The timeline is not the full event stream; unchanged events and standalone coverage records may not appear.

## Validation boundary

For report-v1 comparison files, the browser performs defensive structural checks and verifies evidence-link fields. It does not implement the full JSON Schema or recompute the deterministic report ID, and the report view now displays this boundary beside the loaded report metadata. Use `python -m driftglass report validate ./comparison.json` to validate schema, cross-field relationships, and the content-derived report ID. A structurally valid browser report is not a cryptographically verified export.

## Privacy and security boundaries

The viewer has no backend, history, uploader, local storage, or collector controls. It reads one user-selected file into page memory and caps accepted files at 20 MiB. It renders report values as text rather than HTML. Vite is configured to bind to loopback only.

The dashboard is a review surface, not an isolation boundary. Hostnames, process metadata, paths, and evidence references can be sensitive. A complete report means only that supported input gaps were not declared; it does not prove the app is safe or that every action was observed.

There is no local HTTP API or backend to validate in this prototype. API access-control validation is explicitly deferred until an API is proposed; see the [decision record](decisions/local-api-security-deferral.md).


## Partial process relationship view

The report viewer can draw a partial process relationship view from evidence records that include a validated PID, parent PID, executable, and Linux procfs start-time tick. A parent is linked only if evidence in the same run includes that parent PID with an earlier start tick. Evidence without a start tick is omitted from the tree rather than joined by PID alone. The view includes only process identities referenced by visible findings, not every process observed in the run. The renderer flattens process relationships iteratively, so a long synthetic parent chain does not require one JavaScript call frame per process. Parent candidates are indexed by run and PID, sorted once, and searched by start-time tick to avoid sorting the same candidate list for every child. The viewer renders at most 1,000 process rows per run group for responsiveness; when that limit is reached it displays the full derived identity count and the number of rows omitted from the visual list. The count and internal tree still cover all process identities referenced by the current finding filters, but omitted relationships are not displayed. Visual indentation is capped at eight levels so deep chains stay visible within the viewport; each row still displays its actual computed depth, so indentation does not imply a truncated relationship depth. The existing file-size and token limits still bound accepted imports. Older report files remain valid and continue to open; they may not contain enough identity metadata to populate this view.


## Per-run coverage matrix

The dashboard shows the collection-source declarations and actual input record counts copied into newer report-v1 comparison reports. Rows distinguish a source declared active, declared unavailable, inactive/failed sources, conflicting declarations, and categories not declared. Each run's source list, dropped-event count, and errors can be expanded. Older report-v1 files without this optional snapshot remain readable and show an explicit unavailable state instead of an inferred matrix.

The event counts represent records in the input JSONL presented to the comparator. A zero count does not mean no activity occurred. A declared active source does not prove comprehensive collection.


## Repeat-analysis viewer

The same read-only page can open an exported repeat-analysis-v1 JSON file. It validates the cohort shape, source report IDs/statuses, partial-report list, pattern-to-report references, recurrence labels, and summary counts before displaying the result. It shows recurring and not-consistently-observed patterns separately and preserves source report/finding IDs for manual lookup in the original comparison files.

The browser verifies the repeat-analysis content-derived `analysis_id` using the same canonical JSON rules as the Python exporter before displaying the file. This detects content/ID mismatches but is not a signature: a party can change the file and recalculate its ID. The Python exporter and repeat command remain authoritative for full JSON Schema validation. Source references are not embedded evidence, and the viewer does not load other files automatically. A recurring label means the normalized pattern was present in every supplied report; it is not a maliciousness or safety verdict. Partial runs, sampling and differences in actual environment conditions can affect repeatability.
